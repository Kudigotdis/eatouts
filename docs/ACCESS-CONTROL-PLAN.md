# Access Control Plan — www.eatouts.site

**Status:** Milestones A + B implemented (not yet deployed; the gate ships **off**) · **Last updated:** 2026-11-05
**Scope:** geo-gate for Botswana, revocable admin exception for the Zimbabwe operator,
anti-scrape hardening, structured denial logging.
**Stack:** Cloudflare Pages + Pages Functions, D1, KV (`OPS_KV`), Supabase Storage. No framework.

---

## 1. Why this exists

The directory payload behind `eatouts-about.html` is a single static JSON file
(`assets/data/…`, **728 KB / 567 listings**). The browser fetches it, and nothing gates
it: no cookie, no Function, no rate limit. Anyone with `curl` can pull the whole
dataset in one request, and anyone outside Botswana can browse it freely.

Two requirements pull in opposite directions:

1. The audience is Botswana-only (licensing, payment methods, delivery zones, support).
2. The operator works from **Zimbabwe** and must use the site daily without weakening
   (1) for anyone else.

So the plan is a *layered* gate: cheap checks first, expensive checks last, one
revocable exception for the operator, and every denial attributable so a real Botswana
visitor is never silently locked out for long.

## 2. Phase 0 findings (facts, not assumptions)

| # | Finding | Consequence |
|---|---------|-------------|
| F1 | The 728 KB payload is a static file under `assets/data/` | No Function can gate it today → Milestone C |
| F2 | `_routes.json` (generated by `copy-static.mjs`) excludes `/*.html`, `/assets/*`, `/js/*`, `/css/*`, `/img/*` | A root `_middleware.js` does **not** run for HTML pages; only `/api/*` and unmatched paths reach Functions (`copy-static.mjs` L142–152) |
| F3 | No framework; Pages Functions are plain ES modules with `onRequestGet` / `onRequestPost` | Helpers must be hand-rolled, no middleware library |
| F4 | Sessions are opaque KV tokens in the `eatouts_session` cookie (`_shared.js`) | Cannot carry claims, so the bypass needs its own signed cookie |
| F5 | Passwords use PBKDF2-SHA256 via Web Crypto (`_auth.js`); **no bcrypt/argon2** | Admin password reuses `hashPassword`, no new KDF |
| F6 | `_auth.js` exports `PBKDF2_ITER = 100000` for customer rows | Admin gets its own 600k count, carried inside the secret string |
| F7 | `_headers` already sets `X-Frame-Options`, `nosniff`, `Referrer-Policy` | Only the admin routes needed adding |
| F8 | Tests are CommonJS in `tests/*.js` and import ESM workers via `pathToFileURL` | New suite follows the same pattern; `tests/run-all.js` now runs 76 suites |
| F9 | KV is eventually consistent and the plan tier is unresolved | The bypass must not depend on edge/WAF consistency → D1 tier checks deferred to Milestone D |
| F10 | Every root `*.html` needs an entry in `scripts/html_catalog.meta.json`, a `<!-- PAGE: -->` banner, `data-page` and a line in `copy-static.mjs` | A brand-new admin HTML page costs 4 extra file edits, so the login UI is deferred to Milestone B |

**Decisions taken from these findings (D2–D6):**

| ID | Decision |
|----|----------|
| D2 | Keep the payload static for now; move it behind `/data/*` in Milestone C |
| D3 | `/media/*` HMAC proxy for Supabase in Milestone D |
| D4 | PBKDF2-SHA256 with 600,000 iterations for the admin password |
| D5 | Twilio Verify only when its env vars are present (step-up is optional) |
| D6 | The edge does a *cookie-presence* check; `_middleware.js` does the authoritative HMAC check, which works on any plan |

## 3. The pipeline (seven stages)

```
request
  │
  ├─ Stage 0  Edge WAF rule: no admin cookie AND country != BW   → 403   (dashboard JSON)
  ├─ Stage 1  UA sanity: known-bad crawler signatures            → 403
  ├─ Stage 2  ASN sanity: DATACENTER_ASNS                        → 403
  ├─ Stage 3  Admin bypass: eatouts_admin_bypass HMAC + epoch    → allow (skips 4-6)
  ├─ Stage 4  Geo: country must be BW                            → 403
  ├─ Stage 5  Data: /data/* serves the directory payload         → gated like Stage 4
  ├─ Stage 6  Media: /media/* HMAC-signed, short-lived URLs      → 403
  └─ Stage 7  Denial log: every 403 above lands in denial_log
```

Stages 5–7 are Milestones C and D. Milestone A ships Stage 3 plus the shared module
every later stage imports, because a gate with no way in for the operator would lock
the site for the only person who can fix it. Milestone B ships Stages 1–4 in
`functions/_middleware.js` — but behind `ACCESS_GATE`, so deploying the code changes
nothing until the operator turns it on (see §5).

**Every stage fails closed.** Missing secret, missing binding, unparsable cookie, KV
error → deny. There is exactly one denial body (`Forbidden`, 403) and it never names
the reason, the country, the ASN or the rule, so a blocked scraper learns nothing from
the response.

### 4.2 Token format

```
v1.<base64url(JSON payload)>.<base64url(HMAC-SHA256(secret, "v1.<payload>"))>
```

- `eatouts_admin_bypass` — `{ kind:"bypass", usr, dev, epoch, iat, exp }`, 30 days.
- `eatouts_admin_device` — `{ kind:"device", usr, dev, epoch, iat, exp }`, 365 days.
- Both are `HttpOnly; Secure; SameSite=Strict; Path=/` in production; `Secure` is
  dropped outside production so `wrangler pages dev` can still set them.
- `dev` is `sha256("adm-dev:" + browser|platform)`, so a Chrome auto-update does not
  lock the operator out while a different browser or platform does.

### 4.3 Revocation

`adminGate` requires `token.epoch === OPS_KV["admin:epoch"]`. `revoke-all` increments
that counter, so **every** token ever issued dies at once with one KV write and no DB
read on the hot path. The `admin_devices` rows are also stamped `revoked_at` for the
management screen. A revoked cookie cannot re-revoke.

### 4.4 Why a cookie and not an IP allow-list

The operator's Zimbabwean ISP hands out dynamic CGNAT addresses, and behind Cloudflare's
edge the client IP is not stable across mobile and wifi. A signed, device-bound,
globally revocable cookie survives that; an IP allow-list does not. It also keeps the
exception auditable: every mint is a row in `admin_audit`.

### 4.5 Configuration

| Name | Type | Value |
|------|------|-------|
| `ADMIN_USERNAME` | secret/var | the operator's login name, e.g. `ops` |
| `ADMIN_PASSWORD_PBKDF2` | **secret** | `600000:<saltHex>:<hashHex>` from `scripts/hash-admin-password.mjs` |
| `ADMIN_BYPASS_SECRET` | **secret** | ≥ 32 random bytes; rotating it invalidates every bypass cookie |
| `OPS_KV` | KV binding | already used for sessions; stores `admin:epoch` and login rate-limit counters |
| `DB` | D1 binding | already present; takes the four new tables |
| `ENV` | var | `production` in prod, anything else locally (controls the `Secure` flag) |

Generate the secret, then paste the single printed line into the Wrangler prompt:

```powershell
node scripts/hash-admin-password.mjs 'a long admin passphrase'
npx wrangler pages secret put ADMIN_PASSWORD_PBKDF2
npx wrangler pages secret put ADMIN_BYPASS_SECRET   # paste 32+ random chars
npx wrangler pages secret put ADMIN_USERNAME
```

### 4.6 Deploy order

1. `npm test` — 76 suites green (must include `security-admin.js`).
2. `npx wrangler d1 migrations apply eatouts --remote` — tables first, code second.
3. `npx wrangler pages secret put …` — secrets before the code that needs them.
4. `git push` — Pages builds and deploys automatically.
5. `curl.exe` the checks in §7.

Deploying the code before the migration is the one order that must not happen: the
endpoints swallow DB errors, so the site would look fine while `admin_devices` and
`admin_audit` silently stayed empty.

## 5. Milestone B — the gate (DONE, ships off)

The whole pipeline lives in `functions/_middleware.js` (Pages root scope, so it runs
before every Function) and every stage reuses `functions/api/_security.js`. Nothing is
re-implemented, and `_routes.json` no longer excludes `/*.html`, which is what finally
lets the middleware see a page request.

| Item | Detail | Status |
|------|--------|--------|
| `functions/_middleware.js` | Stages 1–4, `off` / `monitor` / `enforce`, one try/catch that denies on any throw, one generic 403 | done |
| Skip list | `/api/admin/*` (login must work from ZW), `/api/auth/*`, `/api/health`, `/admin/*`, `_headers`, `_redirects`, `_routes.json`, `robots.txt`, `manifest.json`, `favicon.ico` | done |
| `_routes.json` | `copy-static.mjs` no longer excludes `/*.html`; the asset folders (`/assets/*`, `/js/*`, `/css/*`, `/img/*`) stay excluded until Milestone C | done |
| `functions/admin/login.js` | `GET /admin/login` — the one page a non-BW operator can load. A Function, not a `.html` file, so the gate can never block its own only way in. Posts to `/api/admin/login`; 503 when the secrets are absent; 405 for anything but GET/HEAD | done |
| Denial logging live | every stage calls `logDenial` with `{ stage, rule, confidence }`; in `monitor` mode the record is written and the page is still served | done |
| Admin UI | "bypass active until …" + revoke-all + device list inside `eatouts-admin-dashboard.html`, plus a read-only `denial_log` view — see §5.3 | done |
| Step-up (D5) | Twilio Verify only when `TWILIO_*` env vars exist | deferred: optional, unverifiable without live credentials |

### 5.1 `ACCESS_GATE` — why the gate ships off

| Value | Behaviour |
|-------|-----------|
| unset / `off` (deployed default) | the gate is inert: no checks, no rows, no denials |
| `monitor` | every stage runs and each would-be denial is written to `denial_log`, but the request is served |
| `enforce` / `on` / `true` | a denial is the generic 403 |

Two reasons it is not on by default:

1. **Deploy order.** The gate needs the three secrets and a bypass cookie to exist before
   it can be enforced; flipping a variable is reversible in seconds, `git revert` is not.
2. **SEO.** Stage 2 and Stage 4 deny Googlebot and Bingbot (they crawl from US datacenter
   ASNs), so `enforce` takes the site out of search results. That is a product decision,
   not a bug — `monitor` is how you measure it before it happens (`rule='datacenter_asn'`,
   `country` in the row).

Rollout: deploy with `off` → log in at `/admin/login` → set `monitor` → read `denial_log`
for a week and confirm no Botswana visitor and no wanted crawler is in it → set `enforce`.

### 5.2 Stage order, and why the bypass is not on the hot path

Stages 1–2 always run first, so a request that looks like `curl` or arrives on a
hosting-network ASN is refused *whether or not* it carries a valid cookie — a stolen cookie
cannot turn a scraper into a resident, and the operator's own browser is a normal
Chrome/Safari/Edge, so this costs the operator nothing.

Stage 4's test then runs before Stage 3, but only as a short-circuit: a request whose country
is already `BW` cannot need the exception, so it is served immediately and the KV read that
validates the cookie never happens. Stage 3 is therefore evaluated for exactly the traffic
Stage 4 would deny. The set of allowed requests is identical to the §3 ordering; what changes
is that KV reads scale with cross-border traffic instead of with page views (KV has a daily
read quota, and this is the difference between "a few hundred" and "one per page view").


### 5.3 Milestone B2 — the management screen

`GET /api/admin/access?days=7` (new, `functions/api/admin/access.js`) is the only new
read. The dashboard's "Access & security" accordion renders all four parts of B2 from
that one response.

| Panel | Source | Guard |
|-------|--------|-------|
| "Bypass active until …" | `adminGate()` on the request itself | platform_admin session |
| Revoke-all button | `POST /api/admin/revoke-all` (unchanged) | the bypass cookie |
| Device list | `admin_devices` | platform_admin session |
| Refusals, grouped + latest | `denial_log`, `?days=` clamped 1–90 | platform_admin session |

Three decisions worth keeping:

1. **The panel reads with the platform_admin session, not the bypass cookie.** A
   Botswana admin has no bypass cookie and must still be able to see which browsers may
   bypass and revoke a lost one. So the endpoint *reports* the bypass (`active`,
   `expires`, `device`, `current`) instead of requiring it, and only the revoke button
   demands a live cookie — a session alone can never bump the epoch.
2. **It reads; it never writes.** Minting stays in `/api/admin/login`, revocation in
   `/api/admin/revoke-all`. Nothing here can widen access, which is what makes it safe
   to expose to every platform admin.
3. **`ip_hash`, `ua_hash` and `fp_hash` are never selected**, and the suite asserts those
   keys cannot appear in the payload — so this screen cannot become a second, readable
   copy of the identifiers `denial_log` deliberately only stores as hashes. A missing
   table is a `warnings` entry, not a 500: before migration 0018 is applied this panel is
   exactly how you see that it has not been applied.

The gate mode is shown as a pill (`gate off|monitor|enforce`) read through the same
`gateMode()` the middleware uses, so the operator can tell which mode a deployment is in
without opening the Cloudflare dashboard.

Twilio step-up (D5) is **not** built: it is optional, it sits on the single login path,
and it cannot be verified without live `TWILIO_*` credentials. Shipping it inert and
unverified would put untested code in front of the only way into the site.

### 5.4 Milestone C — the payload

Move `assets/data/*` to `/data/*` served by `functions/data/[[path]].js`, behind the
same gate, with `Cache-Control: private, no-store` and an ETag. Update every consumer
(`js/…` readers) in the same commit — this is the change that actually stops the
728 KB scrape, and it is the one with the widest blast radius.

### 5.5 Milestone D — media, tiers, canaries

| Item | Detail |
|------|--------|
| `/media/*` proxy (D3) | HMAC-signed, short-TTL URLs so a hotlinked Supabase asset 403s without a live session |
| Plan tiers (D1) | per-plan gating from D1; deferred because it needs the D1 read on the hot path |
| Canaries | `canary_tokens` ids planted in menus and image names; a hit proves a leak and names the source |

## 6. Failure behaviour and privacy

| Situation | Result |
|-----------|--------|
| `ADMIN_BYPASS_SECRET` missing | `adminGate` → 403, `login` → 503, no token minted |
| `OPS_KV` missing | `adminGate` → 403, `readEpoch` → 0, `login` → 503 |
| D1 missing/unreachable | Admin auth still works; audit and device rows are skipped (best effort) |
| Cookie expired / tampered / wrong `kind` | 403, indistinguishable from "no cookie" |
| Epoch bumped | every existing cookie → 403 |
| Sixth + login attempt from one IP in 15 min | 429 |
| `ACCESS_GATE` unset (the deployed default) | no stage runs, no row is written |
| `ACCESS_GATE=monitor` | the request is served, one `denial_log` row is written |
| `ACCESS_GATE=enforce`, no `cf.country` (local `wrangler pages dev`) | `country_missing` → 403, so the gate is never silently open |
| Any unexpected exception in a handler | 403 (never a 500 that leaks a stack) |

**Privacy stance (same as `0017_venue_interest.sql`):** IP addresses and user agents are
only ever stored as salted SHA-256 hashes (`ip:…`, `ua:…`), never raw, and phone numbers
are never stored for this flow at all. Geo fields (country, ASN) are Cloudflare's coarse
values and are kept because they are what makes false positives triageable. Cookie values
are never logged.

## 8. Rollback

| Change | Rollback |
|--------|----------|
| Cookie leaked | `POST /api/admin/revoke-all` (or bump `admin:epoch` in KV directly) |
| Secret leaked | `npx wrangler pages secret put ADMIN_BYPASS_SECRET` with a new value → all cookies die |
| Endpoints misbehaving | `git revert` the commit and push; the migration stays, and it is additive so nothing breaks |
| Gate blocking real visitors | set `ACCESS_GATE=off` (or `monitor`) in Pages → *Settings* → *Variables and Secrets* — no deploy needed |
| Gate blocking the operator by mistake | `/api/admin/revoke-all` does not help; the operator needs `monitor`/`off`, or a fresh login at `/admin/login` from a normal browser |
| Admin locked out entirely | set `ADMIN_PASSWORD_PBKDF2` for a fresh passphrase; the login endpoint only needs the secret to be present |

The tables are additive (`CREATE TABLE IF NOT EXISTS`) and nothing else in the app reads
them, so a rollback of the code needs no rollback of the schema.
