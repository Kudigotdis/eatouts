# EatOuts — Integration, Wiring & Cloudflare Deployment Guide

This document explains how the ten new files fit into the existing project, **how to wire them so they communicate correctly**, how the whole thing deploys on **Cloudflare Pages**, which existing files must be updated, every `.py` and config file the project needs so it doesn't rebuild from scratch, and what to fill in after integrating. It cross-references the four root docs that govern this work:

- `AI_BUILD_PROMPTS.md` — how to prompt a builder and the hard constraints.
- `NEW_PAGES.md` — the spec for every new/changed page (the acceptance criteria).
- `HTML_PAGES.md` — what the existing root pages do and their limits.
- `MARKETING_ONBOARDING_PLAN.md` — the 29-task launch plan; each page maps to one or more plan tasks.

> **How to read this document.** §1–§2 are orientation. **§3 is the core: the five shared contracts that make the pages talk to each other.** §4 is the step-by-step implementation guide. **§5 is the complete Cloudflare + Python file manifest** — every file the project needs. §6–§7 are the Python scripts and Cloudflare config in full. §8–§14 are reference: existing-file edits, acceptance checks, libraries, placeholders, final checklist.

---

## 0. The one-paragraph summary

Six new pages (`pricing.html`, `get-started.html`, `partner-terms.html`, `intake.html`, `invoice.html`, `ops-console.html`), one print page (`one-pager.html`), and two drop-in libraries (`eatouts-image-compressor.js`, `eatouts-video-validator.js`) were added. They are self-contained HTML files that reuse the existing runtime modules and deploy as static assets on **Cloudflare Pages**. To make them **communicate correctly**, five things must be wired consistently: **one pricing object**, **one ops state key (`eatouts_ops_v1`)**, **one intake draft + export shape**, **one auth gate**, and **one WhatsApp routing rule**. On Cloudflare, the only server-side code is the Python build pipeline (run at build time, never at request time) that turns `owner_submissions/*.json` into `directory_runtime_data.json`. Once the five contracts are honoured and the Python merge script is in place, the intake → export → ops → publish → invoice loop closes. That is what this document wires.

## 3. The five shared contracts (how the pages communicate)

**This is the heart of the integration.** Every new page talks to the others through exactly five channels. If you keep these five consistent, the pages communicate correctly. If you break any one of them, prices drift, state gets lost, or the publish gate fails silently.

### 3.1 Contract #1 — The pricing object

**Owner:** `pricing.html` (the only file allowed to *define* prices).
**Readers:** `get-started.html`, `partner-terms.html`, `invoice.html`, `ops-console.html`, `restaurant-dashboard.html` (after the fix), `one-pager.html` (static text).

**The object** (already defined in `pricing.html`):

```js
var PRICING = {
  currency: 'BWP',
  symbol: 'P',
  setup: 300,
  tiers: {
    starter: { key:'starter', name:'Starter', price:100, blurb:'Get listed and take orders.' },
    growth:  { key:'growth',  name:'Growth',  price:300, blurb:'Add promos, events and bookings.' },
    pro:     { key:'pro',     name:'Pro',     price:500, blurb:'Featured, unlimited, priority.' }
  },
  features: [ /* 8 rows, matrix in NEW_PAGES.md §4 */ ]
};
window.EATOUTS_PRICING = PRICING;

// persist for cross-page reads
try {
  var db = EatoutsDB.load();
  db.settings = db.settings || {};
  db.settings.pricing = PRICING;
  EatoutsDB.save(db);
} catch (e) { /* page still renders */ }
```

**How every reader resolves it** (the exact pattern already used in `invoice.html` / `ops-console.html`):

```js
var PRICING = window.EATOUTS_PRICING || (function(){
  try {
    var s = EatoutsDB.load().settings || {};
    if (s.pricing) return s.pricing;
  } catch(e){}
  return { setup:300, tiers:{ starter:{price:100}, growth:{price:300}, pro:{price:500} } };
})();
if (!PRICING.tiers) PRICING.tiers = { starter:{price:100}, growth:{price:300}, pro:{price:500} };
```

**Rule:** never hardcode a price on any page other than `pricing.html`. If you must show a literal (e.g. in `partner-terms.html` prose), it must be checked against the object during the integration checklist (§13).

**The one edit that keeps this contract honest:** `restaurant-dashboard.html` currently hardcodes `{starter:300, growth:500, pro:800}`. That is drift waiting to happen. Replace it (§8.1 and §4 step 7) with a read from `EatoutsDB.load().settings.pricing`.

### 3.2 Contract #2 — The `eatouts_ops_v1` state key

**Owner:** whoever writes to it. New internal pages only.
**Readers:** `intake.html`, `invoice.html`, `ops-console.html`, `restaurant-dashboard.html` (setup-fee status only).

All new internal state lives under one localStorage key, **separate from `eatouts_db_v2`** (which the operator pages use). The complete shape, taken from the actual files:

```js
// localStorage key: 'eatouts_ops_v1'
{
  venues: [
    {
      id: 'v_xxx', name: '', slug: '', tier: 'starter|growth|pro',
      status: 'draft|ready|live|suspended',
      whatsapp: '',
      nextBilling: 'YYYY-MM-DD' | null,
      setupDate: 'YYYY-MM-DD' | null,
      setupPaid: true|false,
      createdAt: 1234567890
    }
  ],
  invoices: [
    {
      number: 'EO-YYYYMM-001', venue: '', contact: '',
      tier: 'Starter|Growth|Pro', setup: 300, monthly: 100|300|500,
      total: 400|600|800, issue: 'YYYY-MM-DD', due: 'YYYY-MM-DD',
      month: 'YYYY-MM', status: 'unpaid|paid|overdue', at: 1234567890
    }
  ],
  submissions: [
    { slug: '', filename: 'venue_<slug>_<YYYYMMDD>.json', at: 1234567890, by: 'operator' }
  ],
  metrics: [
    { weekOf: 'YYYY-MM-DD', venuesLive: 0, paidSubs: 0, mrr: 0, clicks: 0 }
  ],
  bank: {
    bank: '', acctName: '', acctNo: '', branch: '',
    momo: '', refPrefix: 'EOINV', reg: ''
  }
}
```

**Who writes what:**

| Page | Writes to `eatouts_ops_v1` | Reads from `eatouts_ops_v1` |
|---|---|---|
| `intake.html` | `submissions[]` (on export) | — |
| `invoice.html` | `bank`, `invoices[]` | `bank`, `invoices[]` (for sequence numbers) |
| `ops-console.html` | `venues[]`, `metrics[]` | `venues[]`, `invoices[]`, `submissions[]`, `metrics[]` |
| `restaurant-dashboard.html` | — | `venues[]` (for setup-fee status) |

**Canonical load/save helpers** (already in `invoice.html` and `ops-console.html`; copy verbatim into any new page that needs them):

```js
function opsLoad(){
  try { var r = localStorage.getItem('eatouts_ops_v1');
        return r ? JSON.parse(r) : { venues:[], invoices:[], submissions:[], metrics:[] }; }
  catch(e){ return { venues:[], invoices:[], submissions:[], metrics:[] }; }
}
function opsSave(o){
  try { localStorage.setItem('eatouts_ops_v1', JSON.stringify(o)); }
  catch(e){ console.warn(e); }
}
```

**Rule:** no new internal page writes to `eatouts_db_v2` except through `EatoutsDB` / `EatoutsOwnerCompat`.

**Cloudflare migration note:** when you move off single-device localStorage, swap the two function bodies above to call `/api/ops` (a Pages Function backed by KV or D1). The pages do not change — only these two functions do. See §7.4.

### 3.3 Contract #3 — The intake draft + export shape

**Owner:** `intake.html`.
**Readers:** `ops-console.html` (submissions queue), `scripts/build_restaurant_directory.py` (the merge script, plan task A2).

Two separate things live here:

**(a) The draft** — the concierge's in-progress work. Lives under its own key so it never collides with the ops blob:

```js
// localStorage key: 'eatouts_intake_draft_v1'
{
  id: 'intake_xxx', createdAt: 1234567890, updatedAt: 1234567890,
  identity: { name, slug, description, logo, coverImage, types:[] },
  location: { district, districtName, town, area, plotNumber, street, building, landmark, lat, lng },
  contacts: [...], socials: {...}, hours: { weekly:{}, custom:[] },
  character: [], amenities: [], menuTags: [], capacity: [], payments: [],
  reservations: {...}, reservationServices: [], serviceStaff: [],
  menu: { categories:[ { id, name, items:[...] } ] },
  promos: [], events: [], gallery: { groups:[ { id, title, images:[...] } ] },
  export: { lastExportedAt, filename }
}
```

Draft survives reload because `bindLive()` writes on every input (`draftSave(draft)`). Re-opening `intake.html` calls `draftLoad()` and resumes. No other page reads this key.

**(b) The export** — the file that becomes `owner_submissions/venue_<slug>_<YYYYMMDD>.json`. Built by `buildExportObject()` inside `intake.html`. **This is the shape the merge script must ingest.** It is already shaped to match `directory_runtime_data.json` and the owner content block. The top level is:

```js
{
  $schema: 'eatouts.venue.v1',
  generatedAt, slug, name, description, logo, coverImage, types, category,
  location: {...}, landmark,
  contacts: [...], socials: [...],
  profile: {
    name, identity:{...}, location:{...}, contacts:[...], socials:[...],
    operatingHours:{ title, weekly:[{day,open,close}], customSchedules:[] },
    character:{ title, options:[...] },
    amenities:{ title, options:[...] },
    menuTags:{ title, options:[...] },
    capacity:[], payments:[], reservations:{...},
    reservationServices:[], serviceStaff:[], users:[]
  },
  content: {
    menuCategories:[...],
    menuItems:[...],
    promos:[...], events:[...],
    performers:[], performances:[],
    galleryGroups:[...],
    galleryImages:[...]
  }
}
```

**The intake → ops handshake.** When `intake.html` exports, it does two things in one step (already coded):

```js
// 1. download the file (Blob → <a download>)
// 2. log a submission in eatouts_ops_v1 so ops-console sees it
var ops = opsLoad();
ops.submissions = ops.submissions || [];
ops.submissions.push({
  slug: slug,
  filename: filename,
  at: Date.now(),
  by: (EatoutsAuth.currentSession()||{}).userName || 'operator'
});
opsSave(ops);
```

That is the only channel between `intake.html` and `ops-console.html`. `ops-console.html` renders that array and reminds the operator to copy the file into `owner_submissions/`.

**On Cloudflare, the operator can now skip the manual copy step** if you add a Pages Function `POST /api/submissions` that writes the file into R2 or commits it to the repo via the GitHub API. The intake export already calls `opsSave` — point it at the API instead and the file lands in `owner_submissions/` server-side. See §7.4.

**Rule:** the export shape is the contract with the merge script. Do not add or rename fields without updating `scripts/build_restaurant_directory.py` (§6.1).

### 3.4 Contract #4 — The auth gate

**Owner:** `js/eatouts-auth.js` (existing, not edited).
**Consumers:** all three internal pages (`intake.html`, `invoice.html`, `ops-console.html`).

Every internal page runs this **before any content paints**, immediately after the runtime `<script src>` tags and *before* the page's own `<script>`:

```html
<script src="js/eatouts-db.js"></script>
<script src="js/eatouts-auth.js"></script>
<script src="js/eatouts-brand.js"></script>
<script>
if(!EatoutsAuth.requireSession()){EatoutsAuth.redirectToLogin();}
else{EatoutsAuth.applyActive();}
</script>
<script>
/* page logic starts here */
</script>
```

Already correct in `intake.html`, `invoice.html`, `ops-console.html`. **Public pages (`pricing.html`, `get-started.html`, `partner-terms.html`) must NOT call `requireSession()`.** `get-started.html` and `pricing.html` load `eatouts-auth.js` only so `EatoutsAuth` exists for other helpers; they never gate.

**Rule:** internal pages must not appear in the public tab bar. The existing operator tab bar (`restaurant-onboarding.html` … `restaurant-dashboard.html`) is reused in `intake.html`, `invoice.html`, `ops-console.html` — that is correct, because those pages are only reachable behind the gate. `pricing.html`, `get-started.html`, `partner-terms.html` use a different, simpler top bar and link only to each other and `index.html`.

**Cloudflare note:** if you later add Cloudflare Access in front of `/intake`, `/invoice`, `/ops`, the client-side gate becomes a second layer. Cloudflare Access handles the real protection; the client gate stays as a UX redirect. Do not remove it — it is what makes the pages render correctly when opened directly.

### 3.5 Contract #5 — WhatsApp routing

**Owner:** `index.html` (customer app). **Consumers:** every page that emits a `wa.me` link.

**Today (broken):** every page routes to the flagship `+267 71 844 129`.

**Target:** order / split-bill / booking / promo-enquiry messages route to the **venue's own contact number**, falling back to `CONFIG.whatsapp` when the venue has no number.

**The pattern every page uses to resolve a number:**

```js
var number = '26771844129'; // fallback = flagship
try {
  var s = EatoutsDB.load().settings || {};
  if (s.whatsapp) number = String(s.whatsapp).replace(/[^\d]/g,'');
} catch(e){}
var href = 'https://wa.me/' + number + '?text=' + encodeURIComponent(message);
```

That pattern is correct **for pages that are about EatOuts itself** (`get-started.html`, `pricing.html`, `invoice.html` when the operator is sending an invoice *from* EatOuts, `intake.html` summary). It is **not** correct for `index.html`'s order / booking flows, which must resolve per-venue.

**The rule for `index.html`:** the messaging intent code that builds the `wa.me` URL must first look up the venue being viewed (its record has a WhatsApp contact — the same field the directory data and the intake export populate) and use that. Fall back to `CONFIG.whatsapp` only when the venue has none. This is plan task **A7** and closes blocker #2. See §8.2 for the exact edit.

## 4. Implementation guide — step by step

Do these in order. Each step ends with a verification you can run over `http://127.0.0.1` (local) or your Cloudflare preview URL.

### Step 1 — Land `pricing.html` and confirm the pricing object is the single source

1. Drop `pricing.html` at the project root.
2. Open it. Open DevTools console. Run:
   ```js
   window.EATOUTS_PRICING.setup                 // 300
   window.EATOUTS_PRICING.tiers.growth.price    // 300
   EatoutsDB.load().settings.pricing.setup      // 300
   ```
3. All three must return the same numbers. If `EatoutsDB.load().settings.pricing` is undefined, the try/catch swallowed an error — check that `js/eatouts-db.js` loaded before the inline script.
4. Click the WhatsApp CTA — it must open a `wa.me` link with the prefilled message.

**Verify:** no console errors; tier cards render at 360px (they stack); matrix scrolls horizontally on narrow screens.

### Step 2 — Land `get-started.html` and `partner-terms.html`

1. Drop both at the project root.
2. Open `get-started.html`. The pricing summary card must say **P300** setup and **P100 / month · Starter**, and link to `pricing.html`. The sticky footer WhatsApp button must open a `wa.me` link.
3. Open `partner-terms.html`. Scroll to §2.1–2.2. Every P-number must match `pricing.html` exactly (P300, P100, P300, P500). §2.4 must state the publish-after-setup rule.
4. Cross-links: `pricing.html` → `partner-terms.html` and → `get-started.html`; `partner-terms.html` → `pricing.html` and → `get-started.html`; `get-started.html` → `pricing.html` and → `partner-terms.html`. All must resolve.

**Verify:** no session required (open in a fresh incognito window — both pages load without redirect).

### Step 3 — Land `intake.html`

1. Drop `intake.html` at the project root.
2. Open it. It must redirect to the operator login if no session. Log in, then it must render.
3. Fill the Identity section. Watch the slug auto-fill. Reload the page. **The draft must survive** (loaded from `eatouts_intake_draft_v1`).
4. Check the Location section: District → Town → Area dropdowns must cascade from `botswana_locations.js`. If they are empty, `botswana_locations.js` or `js/eatouts-locations.js` failed to load.
5. Fill a couple of sections, then click **Export JSON**. A file named `venue_<slug>_<YYYYMMDD>.json` must download. Open it — the top-level keys must match §3.3(b).
6. Open DevTools → Application → Local Storage → `eatouts_ops_v1`. There must now be a `submissions` array with one entry.

**Verify:** the export round-trips. Re-open `intake.html`, confirm the draft is still there, and that re-exporting produces the same shape.

### Step 4 — Land `invoice.html`

1. Drop `invoice.html` at the project root.
2. Open it. It must be auth-gated (same as intake).
3. The setup fee field must prefill with `300` (read from the shared pricing object). The invoice number must auto-generate as `EO-<YYYYMM>-001`.
4. Fill the bank card once (bank, account, MoMo, etc.) and click **Save payment details**. Reload. The fields must persist (they are under `eatouts_ops_v1.bank`).
5. Click **Render invoice**. The invoice appears below. Click **Print / Save PDF** → print preview must show **only the invoice** (top bar, tabs, form card, history all hidden by `@media print`).
6. Click **Log as issued**. The invoice appears in the "Issued invoice log" below. Toggle **Mark paid** — the badge flips.
7. Open DevTools → Local Storage → `eatouts_ops_v1` → `invoices`. One entry with `status:'unpaid'` then `'paid'`.

**Verify:** no console errors; the WhatsApp button opens a prefilled `wa.me` message containing the invoice total and reference.

1. Drop `ops-console.html` at the project root.
2. Open it. Auth-gated. The tabs must include Invoice and Ops but **not** intake (intake is reachable only by URL — this is intentional; you may add it to the tab bar if you prefer, but do not add it to the public pages).

It must refuse: a red notice appears, no row is added. Now tick **Setup fee paid** and add again. The row appears with a `Paid` badge and a **Go live** button.

**Verify:** MRR equals the sum of active tiers; a `setupPaid=false` venue can never be set to `ready` or `live`; the invoice "paid" entries appear at the bottom.

### Step 6 — Land `one-pager.html`

### Step 7 — Patch `restaurant-dashboard.html` (three edits)

These are **not optional**. Without them the loop is incomplete.

**(7a) Fix the tiers.** Find the hardcoded billing panel. Replace the old object:

// OLD — delete this

with a read from the shared object:

var PRICING = window.EATOUTS_PRICING || (function(){

**(7b) Add "Export this restaurant".** Next to the existing dashboard actions, add a button that serialises the signed-in restaurant record plus its forked content to a downloadable file:

```js
function exportVenue(){
  var slug = (EatoutsBrand.slugify && EatoutsBrand.slugify(restaurant.name)) || restaurant.slug;
  var content = EatoutsDB.resolveContent(restaurant); // existing API
  var payload = {
    $schema: 'eatouts.venue.v1',
    generatedAt: new Date().toISOString(),
    slug: slug,
    name: restaurant.name,
    /* ...same profile/content shape as intake.html's buildExportObject()... */
    profile: { /* restaurant record */ },
    content: content
  };
  var blob = new Blob([JSON.stringify(payload, null, 2)], { type:'application/json' });
  var url = URL.createObjectURL(blob);
  var a = document.createElement('a');
  a.href = url;
  a.download = 'venue_' + slug + '.json';
  document.body.appendChild(a); a.click(); a.remove();
  URL.revokeObjectURL(url);
}
```

This is plan task **A1**. The exported shape must match `intake.html`'s export so the same merge script ingests both. **If you cannot reuse `buildExportObject()` directly, copy its field names exactly** — the merge script does not care which page produced the file, only that the shape is right.

**(7c) Add setup-fee status.** Read the venue's row from `eatouts_ops_v1.venues[]` (match by slug) and show either `P300 setup paid` or `P300 setup owing` in the billing panel. This connects the owner dashboard to the ops publish gate.

**Verify:** dashboard shows P100/P300/P500; the Export button downloads a `venue_<slug>.json` that opens cleanly; the setup-fee status matches what you set in `ops-console.html`.

### Step 8 — Patch `index.html` (two edits)

**(8a) Per-venue WhatsApp routing.** Find the messaging-intent code that builds the `wa.me` URL for orders, split-bill, bookings, and promo enquiries. It currently uses `CONFIG.whatsapp` (the flagship). Change it so the venue being viewed is looked up first:

```js
// OLD — always the flagship
var number = CONFIG.whatsapp;

// NEW — venue first, flagship only as fallback
function resolveVenueWhatsapp(venue){
  var n = venue && (venue.whatsapp || venue.contactWhatsapp || '');
  if (n) return String(n).replace(/[^\d]/g,'');
  // check the venue's contacts[] for a whatsapp:true entry
  if (venue && Array.isArray(venue.contacts)) {
    var c = venue.contacts.find(function(x){ return x.whatsapp; });
    if (c) return String((c.countryCode||'+267') + c.number).replace(/[^\d]/g,'');
  }
  return CONFIG.whatsapp;
}
```

### 6.1 `scripts/build_restaurant_directory.py` — the critical merge script (plan task A2)

**Purpose:** merges `owner_submissions/*.json` into `assets/data/restaurant_listings/directory_runtime_data.json`. This is the bridge between the intake export and the live directory.

**When it runs:** at build time — locally before `wrangler pages deploy`, or in CI. **Not** at request time.

```python
#!/usr/bin/env python3
"""Merge owner_submissions/*.json into directory_runtime_data.json."""
import json, glob, os, sys
from datetime import datetime, timezone

ROOT = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
RUNTIME = os.path.join(ROOT, 'assets/data/restaurant_listings/directory_runtime_data.json')
SUBMISSIONS = os.path.join(ROOT, 'owner_submissions')
SCHEMA = 'eatouts.venue.v1'


def validate(sub):
    if sub.get('$schema') != SCHEMA:
        return f"bad schema: {sub.get('$schema')}"
    if not sub.get('slug'):
        return "missing slug"
    if not sub.get('name'):
        return "missing name"
    if not (sub.get('location') or {}).get('town'):
        return "missing location.town"
    if not sub.get('contacts'):
        return "no contacts"
    return None


def merge(runtime, sub):
    slug = sub['slug']
    record = {
        'slug': slug,
        'name': sub['name'],
        'description': sub.get('description', ''),
        'logo': sub.get('logo'),
        'coverImage': sub.get('coverImage'),
        'types': sub.get('types', []),
        'category': sub.get('category', ''),
        'location': sub.get('location', {}),
        'landmark': sub.get('landmark', ''),
        'contacts': sub.get('contacts', []),
        'socials': sub.get('socials', []),
        'profile': sub.get('profile', {}),
        'content': sub.get('content', {}),
        'updatedAt': sub.get('generatedAt') or datetime.now(timezone.utc).isoformat(),
    }
    venues = runtime.setdefault('restaurants', [])
    for i, v in enumerate(venues):
        if v.get('slug') == slug:
            venues[i] = record
            return 'updated'
    venues.append(record)
    return 'added'


def main():
    with open(RUNTIME, 'r', encoding='utf-8') as f:
        runtime = json.load(f)

    files = sorted(glob.glob(os.path.join(SUBMISSIONS, 'venue_*.json')))
    if not files:
        print('No submissions to merge.')
        return 0

    added = updated = errors = 0
    for path in files:
        try:
            with open(path, 'r', encoding='utf-8') as f:
                sub = json.load(f)
            err = validate(sub)
            if err:
                print(f'SKIP {os.path.basename(path)}: {err}')
                errors += 1
                continue
            result = merge(runtime, sub)
            print(f'{result.upper()} {sub["slug"]}')
            if result == 'added':
                added += 1
            else:
                updated += 1
        except Exception as e:
            print(f'ERROR {os.path.basename(path)}: {e}')
            errors += 1

    with open(RUNTIME, 'w', encoding='utf-8') as f:
        json.dump(runtime, f, indent=2, ensure_ascii=False)

    print(f'\nDone. added={added} updated={updated} errors={errors}')
    return 0 if errors == 0 else 1


if __name__ == '__main__':
    sys.exit(main())
```

**Shape it ingests:** exactly what `intake.html`'s `buildExportObject()` produces (§3.3b). The `$schema` field is the version gate.

### 6.2 `scripts/validate_submission.py` — shape validator

**Purpose:** standalone check you can run on a single submission before it enters `owner_submissions/`. Useful as a pre-commit hook or a CI gate.

```python
#!/usr/bin/env python3
"""Validate one venue submission file."""
import json, sys

REQUIRED = ['$schema', 'slug', 'name', 'location', 'contacts']
SCHEMA = 'eatouts.venue.v1'


def main(path):
    with open(path, 'r', encoding='utf-8') as f:
        sub = json.load(f)
    errors = []
    for k in REQUIRED:
        if k not in sub:
            errors.append(f'missing {k}')
    if sub.get('$schema') != SCHEMA:
        errors.append(f'bad schema: {sub.get("$schema")}')
    if not (sub.get('location') or {}).get('town'):
        errors.append('location.town empty')
    if not sub.get('contacts'):
        errors.append('contacts empty')
    if errors:
        print('\n'.join(f'x {e}' for e in errors))
        return 1
    print(f'OK {sub["slug"]} is valid')
    return 0


if __name__ == '__main__':
    if len(sys.argv) != 2:
        print('usage: validate_submission.py <file.json>')
        sys.exit(2)
    sys.exit(main(sys.argv[1]))
```

### 6.4 `scripts/seed_from_listings.py` — optional bootstrap

**Purpose:** if you have a CSV or a legacy JSON of restaurants, convert it into the `eatouts.venue.v1` shape once, so the runtime data starts populated. Run once at setup, then never again.

```python
#!/usr/bin/env python3
"""One-time: convert a legacy listings file into eatouts.venue.v1 submissions.

Usage: seed_from_listings.py <input.json> [output_dir]
"""
import json, sys, os
from datetime import datetime, timezone


def slugify(s):
    import re
    return re.sub(r'^-+|-+$', '', re.sub(r'[^a-z0-9]+', '-', (s or '').lower()))


def convert(item):
    slug = item.get('slug') or slugify(item.get('name', ''))
    return {
        '$schema': 'eatouts.venue.v1',
        'generatedAt': datetime.now(timezone.utc).isoformat(),
        'slug': slug,
        'name': item.get('name', ''),
        'description': item.get('description', ''),
        'logo': item.get('logo'),
        'coverImage': item.get('coverImage'),
        'types': item.get('types', []),
        'category': item.get('category', ''),
        'location': item.get('location', {}),
        'landmark': item.get('landmark', ''),
        'contacts': item.get('contacts', []),
        'socials': item.get('socials', []),
        'profile': item.get('profile', {}),
        'content': item.get('content', {}),
    }


def main(src, out_dir='owner_submissions'):
    with open(src, 'r', encoding='utf-8') as f:
        data = json.load(f)
    items = data if isinstance(data, list) else data.get('restaurants', [])
    os.makedirs(out_dir, exist_ok=True)
    for item in items:
        sub = convert(item)
        if not sub['slug']:
            continue
        fn = f'venue_{sub["slug"]}_{datetime.now().strftime("%Y%m%d")}.json'
        path = os.path.join(out_dir, fn)
        with open(path, 'w', encoding='utf-8') as f:
            json.dump(sub, f, indent=2, ensure_ascii=False)
        print(f'WROTE {path}')
    print(f'\nDone. {len(items)} items processed.')


if __name__ == '__main__':
    if len(sys.argv) < 2:
        print('usage: seed_from_listings.py <input.json> [output_dir]')
        sys.exit(2)
    main(*sys.argv[1:])
```

### 7.11 Cloudflare storage migration path

Start with **Model A** (localStorage). Migrate to **Model B** when you need multi-device or shared state.

| Data | Model A (launch) | Model B (scale) |
|---|---|---|
| Pricing | `DB.settings.pricing` in localStorage | Same — static config, ship it in `pricing.html` |
| Intake draft | `eatouts_intake_draft_v1` in localStorage | KV namespace `OPS_KV`, key `draft:<session>` |
| Ops state (venues, invoices, submissions, metrics, bank) | `eatouts_ops_v1` in localStorage | KV `OPS_KV` or D1 database |
| Venue directory | `directory_runtime_data.json` (static) | Same — read-only, serve it static |
| Images / video | URLs only (no uploads) | R2 bucket `UPLOADS` + `functions/api/upload.js` |
| Auth | `EatoutsAuth` (localStorage session) | Cloudflare Access, or a Worker-issued JWT |

**The migration is incremental.** You do not rewrite the HTML pages — they isolate state behind `opsLoad()` / `opsSave()` and `EatoutsDB.load()` / `EatoutsDB.save()`. Swap those two function bodies to call `/api/*`, and the pages keep working.

## 11. The two library files: where they actually get used

`eatouts-video-validator.js` and `eatouts-image-compressor.js` are useful, but the project currently has **no file-upload surface** — every image/video in the existing onboarding pages is a URL or emoji (`HTML_PAGES.md` §Shared constraint 5). So these libraries do not yet hook into any existing page.

### 11.1 Where each library is expected to hook in

The existing onboarding pages accept images only as URLs or emoji. The expected call sites, in priority order:

1. **Gallery image upload (highest value).** `gallery-onboarding.html`; the concierge intake gallery editor in `intake.html`.
2. **Menu item image upload.** `menu-onboarding.html` and the intake menu editor.
3. **Promo image upload.** `promo-onboarding.html` and the intake promo editor.
4. **Cover/logo image upload.** `restaurant-onboarding.html` identity section and the intake identity section.
5. **Video upload (lower priority).** Only relevant if the platform ever accepts venue intro videos, event promo videos, or dish videos.

### 11.2 What the upload surface must provide before either library is useful

A real upload surface needs more than a `<input type=file>`. The project currently stores images as URLs in `localStorage`, so an upload path has to decide **where the file lives** and **what URL it gets**. The options:

- **`localStorage` + `URL.createObjectURL`** — simplest, per-device. Blob URLs are transient.
- **Base64/data URL in `localStorage`** — survives reloads, but inflates storage and hits quota faster (the DB is kept under ~5 MB).
- **R2 via a Pages Function** — the Cloudflare-native path. `functions/api/upload.js` (§7.8) puts the file in R2 and returns a stable URL. This is the target once you migrate to Model B.

For launch, keep URL entry as the primary path, and add the compressor as an **optional** helper the concierge can use when a venue sends actual files.

### 11.3 `eatouts-image-compressor.js` — exact integration plan

**Global exposed:** `EatoutsImageCompressor`.
**Key methods:**
- `compress(file, maxWidth, maxHeight, quality)` → `Promise<Blob>`
- `compressDetailed(file, maxWidth, maxHeight, quality)` → `Promise<{ blob, width, height, originalWidth, originalHeight, originalSize, compressedSize, ratio, savedBytes, type, usedFallback, quality }>`
- `supportsWebP()` → `boolean`
- `isImage(file)` → `boolean`
- `blobToDataURL(blob)` → `Promise<string>`
- `formatBytes(bytes)` → `string`
- `DEFAULTS` → `{ maxWidth:1600, maxHeight:1600, quality:0.82, mimeType:'image/webp' }`

**How to load it:** add one `<script src="eatouts-image-compressor.js"></script>` to any page that needs it, after the existing library scripts.

**Recommended defaults:** photos `1600×1600 @ 0.82`; thumbnails `400×400 @ 0.78`.

**How to consume the result:** if the target field is a URL field (the normal case), convert with `blobToDataURL(blob)` and write that string into the image field. If you have the R2 upload endpoint, POST the Blob to `/api/upload` and write the returned URL instead.

**What NOT to do:** do not silently replace a venue's existing image URL with a compressed blob. Compress when the source is a local File; pass through when the source is already a URL.

### 11.4 `eatouts-video-validator.js` — exact integration plan

**Global exposed:** `EatoutsVideoValidator`.
**Key methods:**
- `validate(file, maxSizeMB, maxDurationSeconds)` → `Promise<{ duration, width, height, size, sizeMB, type, name }>`
- `isVideo(file)` → `boolean`
- `formatSeconds(seconds)` → `string`
- `formatMB(mb)` → `string`
- `DEFAULTS` → `{ maxSizeMB:20, maxDurationSeconds:60 }`

**How to load it:** add one `<script src="eatouts-video-validator.js"></script>` to any page that accepts video. Self-contained.

**Recommended defaults:** `validate(file, 20, 60)` — 20 MB, 60 seconds.

**What it does and does not do:** it checks type, size, and duration; it does **not** transcode or compress video. It does not run reliably on every format on `file://` — some MKV/AVI report no duration and are rejected with `duration-read-failed`.

**Failure codes:** `not-a-video`, `too-large`, `too-long`, `no-metadata`.

**Why the validator may be lower priority than the compressor:** no page asks the user for a video file, video storage is a bigger problem than image storage, and adding a validator without a storage story risks validating files the app cannot keep.

### 11.5 Loading order if both libraries are used on one page

Load them in any order — they do not depend on each other.

```html
<script src="js/eatouts-db.js"></script>
<script src="js/eatouts-auth.js"></script>
<script src="js/eatouts-brand.js"></script>
<!-- only on pages that accept uploads -->
<script src="eatouts-image-compressor.js"></script>
<script src="eatouts-video-validator.js"></script>
```

Internal pages that accept uploads would still gate with `EatoutsAuth.requireSession()` first.

### 11.6 Acceptance checks for the libraries (when wired in)

- `isImage(file)` returns `true` for JPEG/PNG/WebP and `false` for text.
- `compress()` returns a Blob smaller than the input for a large photo; `compressDetailed()` reports `savedBytes > 0`.
- `supportsWebP()` is `true` on modern Chromium/Firefox/Edge; the library falls back to JPEG automatically.
- `isVideo(file)` returns `true` for MP4/WebM and `false` for an image.
- `validate()` rejects with a clear message for oversized/overlong files, resolves with `duration`/`width`/`height` for a valid file.
- Neither library throws on load; both expose their globals on `window`.

### The five contracts in one table

| # | Contract | Owner | Readers | Storage |
|---|---|---|---|---|
| 1 | Pricing object | `pricing.html` | all price-showing pages | `window.EATOUTS_PRICING` + `DB.settings.pricing` |

### The five things that break if you get it wrong

| Mistake | Symptom |
|---|---|
| Hardcode a price outside `pricing.html` | Dashboard shows old numbers; invoice and pricing disagree |
| Write internal state to `eatouts_db_v2` | Operator pages overwrite each other; intake draft disappears |
| Change the intake export shape without updating the merge script | `build_restaurant_directory.py` silently drops fields |
| Call `requireSession()` on a public page | Diners get bounced to operator login |
| Route all `wa.me` to the flagship | Every venue's orders land on EatOuts's phone; blocker #2 stays open |
